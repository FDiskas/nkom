**Fact:** nkom.lt (Nemėžio komunalininkas) sometimes drops the XLSX link for the current quarter's waste schedule and publishes only a PDF (a Google Sheets export). `getScheduleFilesFromPage` in `src/nkomService.ts` scrapes both `.xlsx` and `.pdf` links and only uses a PDF when no XLSX exists for that same waste-type+quarter (grouped via `scheduleGroupKey`) — XLSX always wins when both are published.

**Why the PDF parser (`src/pdfSchedule.ts`) is shaped the way it is:** two naive approaches were tried and failed before landing on the current design — worth knowing before "simplifying" it back:

1. **Row detection cannot use the PDF's horizontal grid lines directly.** The Vietovė (locality) cell wraps across several physical text lines, and the row's other columns (Seniūnija, Sav. diena, day columns, Maršrutas) end up *vertically centered* within that wrapped block rather than pinned to its first/last line. The drawn grid sometimes adds extra dividers inside a wrapped cell and sometimes omits the boundary between two simple adjacent rows, so trusting grid lines for rows produces corrupted data (locality names attached to the wrong route/dates). Fix: rows are rebuilt by treating any physical line with content in Seniūnija or the day/route columns as an "anchor" line, then assigning every wrap-only line (Vietovė or Sav. diena) to whichever anchor is **vertically nearest** to it — wraps can appear both before and after the anchor.

2. **Column bucketing must use a text item's horizontal center, not its start x.** pdf.js merges a whole run of same-styled text into one item, so a wrapped locality line is often a single item spanning most of the Vietovė column's width — but its reported x can start a few points *before* the true column boundary (e.g. when a neighboring cell like Seniūnija is empty on that line, shifting where the run begins). Bucketing on start-x misclassifies it into the wrong column; bucketing on `x + width/2` reliably lands it in the right one.

3. Column *boundaries themselves* come from the PDF's stroked vector lines (grid), filtered to fill-free, near-full-length segments — grid lines are reliable for columns, just not for rows.

4. **Leading page-title text** (above the very first anchor line on a page) is kept as its own separate row rather than merged into the header — otherwise it corrupts `extractMonthColumns`' header detection (a title mentioning a month name would double-count that month's column) while still preserving the schedule year for `extractScheduleYear`.

The output is a plain `CellValue[][]` matching what `XLSX.utils.sheet_to_json` produces, so it needs zero changes to the existing row-parsing pipeline (`extractMonthColumns`, `extractDatesFromRow`, `extractCityCandidates`, etc.) in `nkomService.ts`.

**How to apply:** if PDF-derived events come out wrong (wrong dates for a locality, garbled Vietovė text, duplicate month columns), check the row/column logic in `groupLinesIntoRows` and `bandIndex` in `src/pdfSchedule.ts` first — the fixture test `src/pdfSchedule.test.ts` (using `src/fixtures/nkom-schedule-sample.pdf`) pins the exact expected row reconstruction for page 1 of a real schedule PDF.

**Fact (2026-09-28 incident):** the combined "Grafikas pakuočių" PDF (Stiklas + Plastiko/popieriaus/metalinės pakuotės in one file) has no separate section row above its month header, unlike XLSX exports. Each waste-type label (e.g. "Plastiko, popieriaus ir metalinės pakuotės") is drawn as one merged cell spanning a 3-month group (Spalis/Lapkritis/Gruodis) and lands, via `pdfSchedule.ts`'s centerX column bucketing, concatenated onto that group's *middle* month header cell (observed: always Lapkritis) rather than in a row of its own. `extractMonthColumns` in `src/nkomService.ts` used to only look at the row *above* the header (`inferEventTypeFromSectionRow`), so for this file every column's `eventType` came back `null` and all dates fell back to the file-level default type "Pakuotės/Stiklas" — collapsing "Stiklas" and "Pakuotės" (plastic/paper/metal) into one indistinguishable label, e.g. showing a packaging pickup date as "Pakuotės/Stiklas" when it was really glass, or vice versa. Fixed by checking each month column's *own* header cell first (`classifyWasteTypeLabel`), then propagating a found label across its repeating-month group (`fillRepeatingMonthGroups`, which splits groups wherever the month sequence stops increasing) before falling back to the old section-row lookup for XLSX-style layouts. Regression test: `src/nkomService.test.ts` → "splits repeating month groups by the label merged onto one of their own header cells".

**Fact (2026-09-28, same-day follow-up):** `groupLinesIntoRows`'s "consecutive anchor lines form one row" heuristic (see point 1 above) had a second failure mode, found by pulling nkom.lt's *live* Q4-2026 PDFs (no XLSX exists for that quarter, so this is the production path today, not a hypothetical): when two real data rows both fit their Vietovė/Sav. diena on a single line each — no wrap needed — there's no wrap-only line between them to keep their anchor lines apart, so they were glued into one garbled row (e.g. "Kalvelių Lavoriškių Marijampolio Marijampolio..." mashing 5+ distinct localities' Seniūnija/Vietovė/Maršrutas together). Confirmed against live data: this dropped ~24 rows (of ~140) from the mišrių PDF into unreadable blobs before the fix. Fixed by giving Seniūnija (column 0) special status as each row's identity marker (`ROW_IDENTITY_COLUMN`): a later anchor line only merges into the block above it if it does *not* carry its own Seniūnija while that block already has one from an earlier line — which still lets the legitimate multi-line merges through (the packaging-PDF section-label line above has no Seniūnija of its own, and a wrapped Maršrutas continuation likewise has none), while splitting genuine back-to-back rows apart. Regression tests: `src/pdfSchedule.test.ts` → `describe("groupLinesIntoRows", ...)` (three cases: back-to-back split, section-label merge preserved, wrapped-continuation merge preserved). `groupLinesIntoRows` and the `Item` type are now exported from `pdfSchedule.ts` solely so these tests can drive it with synthetic lines without needing a new binary PDF fixture.

**Fact (2026-09-28, third same-day fix):** nkom.lt's source Google Sheet has a trailing tab for "shared apartment-block container-yard" pickups ("... atliekų surinkimas iš (daugiabučių namų) bendro naudojimo konteinerių aikštelių") — a *different* schedule model keyed by weekday + week-parity code (e.g. "Pirmadienis" → "KP1"/"KS1"), not tied to specific calendar dates, and irrelevant to this app's per-locality date lookup. `XLSX.utils` in `readScheduleRows` only ever reads the workbook's *first* sheet, so this tab never surfaced there — but the PDF export concatenates every tab as extra trailing pages, and `readPdfScheduleRows` reads all pages, so it leaked into parsed rows (polluting the city dropdown with nonsense candidates and, once, a real PDF-merge artifact gluing the section's title onto the last genuine data row). Fixed with `dropSharedContainerSection` in `src/nkomService.ts`, called from `readScheduleRows` for both formats (a no-op for XLSX): finds the first row whose text contains all three of "surinkimas", "bendro naudojimo", "aikstel" (normalized) and slices the data to end just before it. Note "bendro naudojimo" *alone* is not enough — it's also a legitimate address suffix ("... bendro naudojimo ir įmonės") on real schedule rows; the three-token conjunction is what avoids that false positive. Regression tests: `src/nkomService.test.ts` → `describe("dropSharedContainerSection", ...)`.
